# 話題のつながりを確認する例

## 1. 配置理由を確認できない例

対象文:

```markdown
# 認証失敗への対応

認証に失敗した場合、利用者へ再ログインを案内します。

## Redis

Redisの接続timeoutは5秒です。
```

`review` の出力例:

```text
[MEDIUM]
対象: 「Redis」節

問題:
前段は認証失敗後の利用者対応を説明していますが、Redisをこの文書・この位置で扱う理由は本文から
確認できません。

読者への影響:
Redisが認証失敗への対応に必要なのか、別の運用情報なのかを推測する必要があります。

確認できたこと:
Redisの接続timeoutが5秒であることは記載されています。

追加で必要な情報:
Redisの役割、認証失敗との関係、この節を現在位置へ置く理由。

対応:
関係を確認できないためRedisを不要とは判断せず、原文も変更しません。
```

接続詞を足しても解決しない。

```text
また、Redisの接続timeoutは5秒です。
```

`また` は意味上のrelationを示さないため、配置理由は依然として分からない。

## 2. 本文から安全なbridgeを作れる例

対象文には、すでに次の関係が明記されている。

```markdown
refresh tokenはserver側で保持します。保存先にはRedisを使います。

認証失敗時は再ログインを案内します。

## Redis設定

接続timeoutは5秒です。
```

`revise-safe` では、確認済みの保存関係だけを節の入口へ再提示できる。

```markdown
refresh tokenはserver側で保持します。保存先にはRedisを使います。

認証失敗時は再ログインを案内します。

## Redis設定

refresh tokenの保存先として使うRedisでは、接続timeoutを5秒に設定します。
```

この改稿では `refresh token`、server側での保持、保存先、Redis、5秒を維持する。高可用性、
session共有、永続化など、元文にない目的は追加しない。

## 3. 安全にbridgeを作れない例

```markdown
refresh tokenの失効条件を説明します。

## Redis設定

接続timeoutは5秒です。
```

topicが近く見えても、tokenをRedisへ保存するとは書かれていない。`revise-safe` では本文を変更せず、
次を返す。

```text
対象: 「Redis設定」節
確認できたこと: 前段はrefresh tokenの失効条件を扱っています。
不足していること: Redisの役割と、token失効との関係。
修正しなかった理由: 保存関係や因果を追加すると、原文にない設計意図を作る可能性があります。
安全に行える範囲: 現在の文を維持し、関係の確認事項を本文外へ示します。
必要な情報: Redisを使う目的、この節の対象、失効処理との関係。
情報が得られた場合: 短いbridgeの追加、または別の設定・運用節への移動を検討できます。
```

## 4. 直前項目と接続しなくてよい例

```markdown
# option一覧

## `--format`

出力形式を指定します。

## `--output`

保存先pathを指定します。
```

二つの項目は「option一覧」という見出しをanchorにしており、互いに因果関係を持つ必要はない。
`independent-under-heading` としてno-changeにする。FAQ、用語集、error code、設定一覧でも、分類見出し
との関係が明確なら同様に扱う。

ただし、list形式でも手順は独立項目ではない。

```markdown
1. 新しい証明書を配布します。
2. 新しい証明書で接続できることを確認します。
3. 古い証明書を失効します。
```

この場合は配布、確認、失効の順序と上位goalとのrelationを確認する。

## 5. 同じ語が続いていても論点が切り替わる例

```markdown
この制度では、申請者が利用目的を登録します。

この制度の費用は、利用者数に応じて増えます。

予算上限を超えた申請は翌月に回します。
```

「この制度」という語は続いているが、最初の段落は申請情報、次の段落は費用を説明している。共通語だけで
つながっていると判定せず、段落の役割、述語、問い、評価軸の切替えと、前段から次段を予測できるかを
確認する。

最後の段落は予算に関係しそうに見えても、利用目的の登録から費用へ進む理由や、予算上限と利用者数の
関係を一意に示さない。この例はcandidateとして保持し、`revise-safe`では並べ替えもbridge追加も
行わない。

安全に並べ替えられるのは、次のように関係が原文に明示されている場合である。

```markdown
この工程では、最終的な採否を担当者が判断します。

この工程にかかる時間は、確認対象の件数に応じて増えます。

採否を判断するには、確認対象をすべて調べる必要があります。
```

最後の段落が判断と確認対象を明示的に結び、時間が対象件数に応じることも本文にある。この場合は、
「判断の所在→全対象を調べる必要→対象件数に応じた時間」の順へ既存の3文だけを並べ替えられる。

```markdown
この工程では、最終的な採否を担当者が判断します。

採否を判断するには、確認対象をすべて調べる必要があります。

この工程にかかる時間は、確認対象の件数に応じて増えます。
```

変更前後で、隣接による含意を含む因果、scope、時系列、強調、確信度が変わらないことを確認する。

## 6. 改稿後の初見確認

可能なら改稿担当とは別のcontextへ、改稿後本文、想定読者、文書目的、必要なtechnical contextだけを
渡す。改稿理由、どこを直したか、元の作業表、期待する答えは渡さない。

初見確認では、現在の話題、前段・見出し・目的との関係、新概念の準備、前へ戻らず理解できるか、
次に何を説明するか予測できるかを確認する。別contextを利用できなければ同一Agentで補助passを
行い、独立性の限界を明記する。

coverage summary例:

```text
確認済みblock: 12
話題のつながりに関する指摘: 1
変更不要として確認した候補: 3
追加情報が必要な候補: 1
構造上の限界: 0
未確認範囲: 0
fresh-reader pass: partial（同一Agentによる補助pass）
```

候補数を終了条件にせず、全eligible blockとglobal passを確認する。

## 7. 止まる動作と続く動作を対応付ける例

次の文は、停止と継続の対象が分かれている。

```markdown
gatewayは新規requestの受付を停止します。
workerは受付済みrequestの処理を完了まで続けます。
```

止まるのはgatewayによる新規受付であり、続くのはworkerによる受付済みrequestの処理である。
主体、動作、対象が異なるため、停止と継続が併記されていることだけでは矛盾として扱わない。
また、「operatorがgatewayの受付を停止する」では、状態変化を起こすoperatorと、受付動作が止まる
gatewayを区別する。

次の文では対応関係を確認できない。

```markdown
障害を検知すると停止します。
その後も処理を続けます。
```

`review`では、何が何を停止し、誰のどの処理が続くのかをcandidateとして示す。system、gateway、
workerなどを推測して本文へ補わない。同じ主体・動作・対象が停止後も続く意味なら、再開条件や別phaseが
必要か確認する。異なる動作を指すなら、それぞれの主体と対象を確認する。

慣用表現でも同じ確認を行う。

```markdown
根拠がそろわず行き詰まると、追加確認がいつまでも完了しません。
```

「行き詰まる」を活動全体の停滞と読むと、追加確認が未完了であることとの関係が曖昧になる。一方、
本来の選定が進まず、追加確認が未完了のままになる意味なら過程は成立する。前段から本来の動作が
候補の選定だと確認できる場合、`revise-safe`では未完了状態を能動的な継続へ変えず、次のように書ける。

```markdown
根拠がそろわないと、担当者は候補を選定できず、追加確認がいつまでも完了しません。
```

進まない動作と未完了の動作を別々に示し、「行き詰まる」を単に「何もしない」と言い換えない。確認を
能動的に続けることが別の文から確認できる場合だけ、「確認を続ける」と明示する。
