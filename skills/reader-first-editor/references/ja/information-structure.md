# 日本語の情報構造

## 段落の役割を早く示す

段落ごとに、主張、結論、理由、条件、例、注意、手順、次の行動のどれを担うか確認する。
読者が段落の後半まで役割を判断できない場合は、見出し、冒頭文、接続のいずれかで方向を示す。
ただし、結論先行が期待や対人配慮を壊すジャンルでは無理に移さない。

## 既知情報から新情報へ

前文で共有した対象を起点にし、新しい条件や判断を後ろへ置く。毎文で別の対象を文頭に置くと、
読者には主題が切り替わったように見える。逆に、主題が変わったのに省略を続けると、誰が責任を
持つのかを誤読させる。

## 主張と補足に強弱を付ける

- 主要結論を、長い背景説明や例の中へ埋めない。
- 条件・例外は主要文との関係が分かる位置に置く。
- 例は例と分かる標識を使い、規則と同じ強さで書かない。
- 注意は対象となる手順・判断から離しすぎない。
- 同じ内容の再要約は、判断や記憶を助ける役割がなければ候補として指摘する。

## 見出し・箇条書き・表

見出し・箇条書き・表は、列挙項目が並列で、読者が項目を比較したり必要な情報を探したりするときに
使う。条件と結果、原因と対策など、異なる役割を同じ箇条書きへ平板化しない。短い連続文まで
箇条書きにして論理を失わせない。表はセル内の長文を隠す目的で使わない。

## 列挙の粒度を確認する

同じ文、箇条書き、表の同じ列に置かれた要素は、表面の文法形だけでなく、何を対象にし、どの役割を
担い、どのscopeと抽象度で述べているかを比較する。

```text
要件を決め、設計し、判断する。
```

「要件を決める」「設計する」が具体的な作業である一方、「判断する」の対象がなく、それらを包む
上位概念にも読める。何を判断するのか、三項が独立した作業なのか階層関係なのかを周囲から確認し、
一意に戻せなければ粒度不一致のcandidateとする。

次のように判断対象が具体的なら、動詞そのものを理由に指摘しない。

```text
要件を決め、画面を設計し、公開可否を判断する。
```

上位概念と下位項目を併記する場合も、「具体的には」「次の作業を含む」などで階層関係が明示されて
いれば同列比較を強制しない。列挙の粒度差が意図的か、scope・担当・完了条件を誤認させるかを確認して
からfindingにする。抽象的な項目を機械的に削除せず、原文にない対象や階層を補わない。

## 括弧書きと本文の関係を確認する

括弧書きを一律に補足または省略可能な情報とみなさない。本文から括弧内を外した場合と残した場合を
比べ、読者の理解、判断、検索、行動、claimの強さがどう変わるかを確認する。

| 関係 | 確認 | 扱い |
|---|---|---|
| 例示 | 本文だけで意味が成立し、括弧内が具体像を与えるか | 具体像が読者を助けるなら維持する。括弧の存在だけで蛇足にしない |
| 定義 | 括弧内を外すと用語、略語、対象を理解・検索できなくなるか | 初出付近に保持する。括弧外へ移す場合も定義と用語の対応を失わない |
| 条件・留保 | 対象、期間、例外、適用条件、不確実性、結論の強さを変えるか | 従属的な補足として隠さず本文へ出し、scopeとmodalityを保つ |
| 蛇足候補 | 本文と同じ内容に見え、判断、検索、対比、記憶、強調、語調に新しい役割を持たないか | 括弧あり／なしの意味台帳を比較し、意味合いを壊さないと確認できた場合だけ削除を検討する |

この分類は閉じたenumではない。citation、出典、単位、読み、別名、識別子などは、定義・検索・検証に
必要な役割を別に持ち得る。code、関数呼出し、正規表現、Markdown linkなどを、括弧という区切りだけで
proseの補足として扱わない。

一つの括弧内に複数の関係がある場合は、括弧全体を一種類へ決め打ちしない。

```text
timeout時のみ再試行します（30秒を超えた場合。例: 外部APIが応答しない場合）。
```

前半は再試行条件であり、後半は具体像を与える例である。条件は本文へ出し、例は必要なら括弧に残せる。
逆に、次のような定義は括弧のままでも理解と検索に寄与する。

```text
OpenID Connect（OIDC）を使います。
```

蛇足かを判定するときは、言い換えられているだけで同じ事実か、例・対比・検索語・読み方・scope、
強調、緊急性、語調を追加していないかを確認する。削除前後の意味台帳を比較し、factsだけでなく
conditions、exceptions、modality、reader action、registerも変わらない場合にだけ削除を検討する。
`review`では削除せず問題と影響を報告する。`revise-safe`では条件・留保を本文へ移せるが、蛇足候補の
削除は行わない。`revise-structural`でも明示的な削除許可がなければ候補だけを示す。
候補を示す場合は、対象の引用または位置と候補actionを付ける。削除を望むユーザーが対象候補を明示
できるようにし、対象と許可を確認した後も、その箇所について削除前後の意味台帳を再確認する。

## 読後の状態

文書を読んだ後に求められるのが、理解、判断、実行、返信のどれかを確認する。原文に行動がある
場合は、主体・対象・期限・条件・返信要否を探しやすくする。原文にない要素は追加せず、
必要なら不足として指摘する。
