# 関係を一語で済ませていないか

## 目的

抽象的な管理語や関係語を使っていることだけでは問題にしない。その語だけでは実際の
運用関係が決まらず、読者が別の箇所やリポジトリ構成を調べて補う必要がある場合に診断する。

指摘の焦点は単語の難しさではなく、文章から次の判断や行動に必要な関係を読み取れるかに置く。
作者がAIか人間かは判定に使わない。

## 単語ではなく省略された関係を見る

「正本」「担保」「連携」「反映」「対応」「整合」などは、文章を見直すきっかけにすぎない。
禁止語でも網羅的な一覧でもなく、出現回数を品質指標にしたり、語の存在だけで指摘したりしない。
同じ語でも、必要な関係が周囲に明示されていれば維持する。

長文のcoverage-driven reviewでは、次の初期候補語を
`scripts/scan_relationships.py` で決定的に列挙できる。marker内はscannerが読むため、書式を
変更する場合はscannerのtestも更新する。

<!-- relationship-tripwires:start -->
- `正本`
- `source of truth`
- `source-of-truth`
<!-- relationship-tripwires:end -->

scannerの結果はcandidateでありfindingではない。全出現箇所を文脈で確認し、法務・記録管理上の
用法、文書内で一意に定義された用法、必要な関係が周囲に明示された用法は除外理由を残して
`excluded` とする。scannerを利用できない場合はLLM-onlyで確認を続け、coverageを `partial` と
して未実施を記録する。

例えば、次の一文だけでは関係を一意に決められない。

```text
SKILL.mdを正本とする。
```

この文は、直接編集するファイル、ホスト別ファイルの生成元、内容が食い違った場合の
優先先、複数のホストが共有する定義、承認済みの正式版などを指し得る。一つを推測して
書き換えず、文章またはリポジトリ内の証拠から実際の関係を確認する。

## 確認する関係

| 次元 | 確認内容 |
|---|---|
| 対象 | 何と何の関係か |
| 種類 | 参照、生成、同期、優先、承認、所有、検証などのどれか |
| 方向 | どちらからどちらへ作用するか |
| 変更点 | どのファイル、設定、記録を直接変更するか |
| 優先 | 内容が異なる場合にどれを採用するか |
| 主体 | 誰・何が判断、実行、承認、生成するか |
| 時機 | いつ、何をきっかけに行うか |
| 完了条件 | 何を確認すれば完了、整合、対応済みといえるか |
| 範囲 | どのホスト、バージョン、文書、環境まで適用するか |
| 根拠 | その関係をどの資料、実装、決定から確認できるか |

毎回すべてを列挙しない。対象読者が目的を達成するために必要で、現在の文章からは確定できない
次元だけを扱う。単独の一文へ背景情報をすべて詰め込むことや、表の全項目を満たすことを
要求しない。

## 指摘する条件

次の条件をすべて満たす場合に指摘する。

1. 抽象語が複数の具体的な関係を表し得る。
2. 周囲の文だけでは、実際の関係を一意に確定できない。
3. 不明な関係が、読者の理解、判断、変更、実行に影響する。
4. 読者が別の箇所やリポジトリ構成を調べて補う必要がある。

## 指摘しない条件

### 法務・記録管理上の具体的な用法

```text
署名済み契約書の正本を法務部が保管する。
```

原本、正本、謄本、写しなどの区別を担う実務用語は、平易さだけを理由に置き換えない。

### 文書内で定義されている用法

```text
本手順では、承認済みPDFを「正本」と呼ぶ。
```

定義により対象が一意なら、語の存在だけでは指摘しない。定義が循環している場合や、運用に
必要な関係がなお分からない場合は、その不足を別に指摘する。

### 実際の関係が続けて明示されている用法

```text
SKILL.mdを管理上の正本とする。
変更はSKILL.mdにだけ加え、ホスト別ファイルはそこから生成する。
```

後続文から変更点と生成方向が分かるため、「正本」を別の語へ置き換える必要はない。

### 読者の判断に必要な関係が明示されている用法

```text
内容が異なる場合は、SKILL.mdの記述を優先する。
```

この文からは、内容が食い違った場面で採用する資料が分かる。このルールでは、比較対象を
文中にすべて列挙していないことだけを理由に指摘しない。比較対象や対象範囲がないために
読者が実際の判断を誤る根拠がある場合だけ、その不足を扱う。

```text
同じSKILL.mdをCodexとCopilotの双方で読み込み、代表的な評価ケースが両方で成功することを
確認する。
```

この文では、確認する対象、方法、完了条件が示されている。評価ケースをこの一文ですべて
列挙していないことだけを理由に、関係が省略されているとは判定しない。

### 専門分野で必要な用語

正式名称、規程、契約、記録管理、認証制度などで用語を保持する必要があり、対象読者も
意味を理解できる場合は維持する。必要なら用語を残したまま説明を加える。

## `正本` と英語の管理表現

ソフトウェア文書では、`source of truth`、`canonical source`、`authoritative source` などに
対応する語として「正本」が使われることがある。ただし、どの英語表現に由来するかは判定の
根拠にしない。これらの表現も文脈によって示す関係が異なるため、固定した訳語へ置き換えず、
実際の関係を直接記述する。

```text
# 不一致時の優先先
内容が食い違う場合は、SKILL.mdの記述を優先する。

# 複数のホストが共有する定義
CodexとCopilotが共有する挙動は、SKILL.mdに定義する。

# 直接編集するファイルと生成方向
SKILL.mdだけを直接編集し、ホスト別ファイルはビルドスクリプトで生成する。
```

生成元、直接編集するファイル、正式公開版、不一致時の優先先、実行時に使われる値、記録上の
原本、承認済み版、共有定義を同じ関係として扱わない。

## その他の代表的な表現

- 「互換性を担保する」では、対象機能、確認方法、合格条件が必要か確認する。
- 「設定を反映する」では、入力元、反映先、実行のきっかけ、実行主体が必要か確認する。
- 「システムを連携させる」では、何をどちらへ渡し、失敗時にどう判断するかが必要か確認する。
- 「対応済み」「整合済み」では、何を確認すれば完了といえるかが必要か確認する。

「担保」を「確保」、「反映」を「適用」、「整合」を「一致」へ置き換えるだけでは、関係の
不足を解消できず、意味を変える場合もある。必要な関係や動作を書く。

## モード別の扱い

### `review`

原文を変更しない。省略された関係の候補を分け、読者が何を調べ、どの判断を補う必要が
あるかを説明する。既定の利用者向け出力では内部識別子を出さない。分類名が必要な場合は
「関係の省略」とし、具体的な不足と読者への影響を併記する。

### `revise-safe`

対象文書の周囲の文と、依頼文に示された文脈から関係が一意に確定できる場合に限り、
関係を直接書く。確定できない場合は一つを選ばず、原文の曖昧さを残すか、
`[要確認: 不一致時に優先する資料]` のように本文外で示す。抽象語を別の抽象語へ
機械的に置き換えない。

### `repository-review`

生成スクリプト、生成されたファイルであることを示す記載、ADR、実行時の既定値、編集方針など、同一
リポジトリ内の証拠から関係を確認する。証拠が競合する場合は確定しない。生成元と不一致時の
優先先を同一視せず、参照回数を優先関係の証拠にしない。

### `authoring`

要件を一語で済ませず、既知の関係を直接書く。不明な関係は創作せず、次のように示す。

```text
[TODO: 直接編集するファイルを指定]
[TODO: 内容が食い違った場合の優先先を指定]
[TODO: 互換性の確認方法と完了条件を指定]
```

### `jtf-only`

適用しない。関係の明確化は内容や構造の変更になり得るため、表記対象がなければ原文を維持する。

## 重大度

- `HIGH`: 誤ったファイルの編集、生成されたファイルへの上書き、誤った優先先、責任主体の誤認、
  手順・安全性・法的な原本性の誤解につながる。
- `MEDIUM`: 別資料やリポジトリ構成を確認しなければ設計・運用意図を判断できない、または
  読者ごとに異なる解釈になり得る。
- `LOW`: 周囲から関係をほぼ一意に判断でき、主要な判断や行動には影響しない。

重大度を単語ごとに固定しない。実際に不足している関係と読者への影響から決める。

## 禁止事項

- 候補語の出現だけで指摘を作らない。
- grep結果や出現回数を品質判定に使わない。
- 作者がAIか人間かを判定しない。
- 法務・記録管理上の用語を平易さだけで置き換えない。
- 関係が不明なまま、もっともらしい一つを選ばない。
- 新しいRR IDを追加しない。
