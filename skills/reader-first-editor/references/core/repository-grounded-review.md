# リポジトリ内の証拠に基づく校閲

`repository-review` は、対象文書の主張を同一リポジトリ内の証拠と照合し、fileを変更せずに
結果を報告する校閲モードである。リポジトリ外の一般的なfact checkingは行わない。目的は、
読者が文書の記述とリポジトリの実態との関係を判断できるようにすることである。コード、
テスト、文書のいずれかを無条件に正解とはみなさない。

## 対象と境界

対象文書と探索範囲を最初に固定する。対象文書から参照されるファイル、文書内の
識別子、設定キー、コマンド、既定値、API名などを起点に、関係を説明できる範囲へ
段階的に探索を広げる。大規模リポジトリを無条件に全件走査しない。

確認対象になり得る証拠は次のとおりである。

- 実装コード、設定、schema、default値、CLI・API定義、UI文字列
- test、fixture、sample、migration、CHANGELOG
- README、設計書、runbook、ADR、リポジトリ内に固定された参照資料
- Git履歴。ただし、履歴依存の主張、明示依頼、証拠競合の文脈確認に限る

外部URLの内容は自動取得しない。モデルの記憶や一般知識を、リポジトリ内の証拠や
外部検証済みの証拠として扱わない。現在のファイルと過去の履歴も区別する。

## claimを抽出する

対象文書から、リポジトリ内の証拠と照合できる主張を抽出する。特に、default値、環境変数、
手順、対応範囲、version、期限、保証、SLA、「推奨」「標準」「安全」「高速」「互換」などの
評価語、因果関係を確認する。単なる意見や将来案を、現在の実装に関する断定へ読み替えない。

各claimについて、次を記録する。

- 原文と位置
- 検証に必要な証拠の種類
- 探索したpathと検索語
- 見つかった証拠と、その位置付け
- 判定不能にする不足や競合

## 判定状態

判定は次の5種類だけを使う。

判定順は、リポジトリ内の反証・支持、外部citationの存在、外部最新情報の必要性、
その他の根拠不足の順とする。外部serviceの現在の提供状況など、リポジトリ外の
最新情報なしに真偽を確認できないclaimは `UNVERIFIED` である。citationがないことだけを
理由に `UNSUPPORTED` へ変えない。

### `VERIFIED`

リポジトリ内の具体的な証拠がclaimを支持する。証拠のfileと位置を示す。支持する
証拠があっても、別の有力な証拠と競合する場合は `VERIFIED` にせず競合を報告する。

### `CONTRADICTED`

リポジトリ内の具体的な証拠がclaimと明確に矛盾する。根拠が見つからないだけでは
この状態を使わない。また、どちらが正しいかをsource-of-truthの根拠なしに決めない。

### `SUPPORTED-BY-CITATION`

外部URL、引用、書誌情報などがclaimの根拠としてリポジトリ内に提示されている。
確認できたのはcitationの存在であり、外部資料の内容、最新性、claimとの一致ではない。
URL先を検証していない限り、外部主張を `VERIFIED` と表現しない。

### `UNSUPPORTED`

探索範囲内に、claimを支持するリポジトリ内証拠も明示的な外部citationも見つからない。
これは誤り判定ではない。探索範囲を示し、必要な根拠の提示を求める。

### `UNVERIFIED`

claimの検証にリポジトリ外の最新情報や外部資料の内容確認が必要で、今回の範囲では
確認できない。モデル知識で不足を埋めない。外部確認が必要な事項を示す。

## 証拠の種類

指摘には、主な照合関係を一つ以上付ける。

- `[DOC↔CODE]`
- `[DOC↔CONFIG]`
- `[DOC↔TEST]`
- `[DOC↔DOC]`
- `[DOC↔HISTORY]`
- `[CITATION]`
- `[EVIDENCE-GAP]`
- `[UNVERIFIED]`

同じclaimに複数の関係がある場合は併記できる。ただし、分類名だけでは何を確認したか
分からないため、必ずfileと位置または確認したcitationを示す。

支持・反証の証拠もcitationも見つからない `UNSUPPORTED` には
`[EVIDENCE-GAP]` を使う。外部の最新情報が必要な `UNVERIFIED` には
`[UNVERIFIED]` を使う。両者を「根拠がない」という一つの分類へまとめない。

## 証拠が競合する場合

コード、test、設定、文書のどれも古い可能性がある。一律の優先順位を設けず、
source-of-truth宣言、ADR、generated marker、runtime default、deprecated・experimentalの
表示、対象versionやbranchを確認する。権威付けを判断できなければ、競合する証拠を
並べ、どれを正とするかは未確定と報告する。

generated・vendor・third-party fileは、その位置付けを確認せずsource of truthにしない。
exampleやfixtureについても、規範的な仕様なのか、説明用の一例なのかを区別する。

## 探索範囲

探索は次の順で必要な範囲だけ行う。

1. 対象文書と、その文書が明示的に参照するlocal fileを読む。
2. claimに含まれるliteral、識別子、設定キー、command、default値を検索する。
3. 見つかった定義のcaller、consumer、test、設定例、関連文書を確認する。
4. 証拠が競合する場合、source-of-truth宣言やADRを探す。
5. 履歴依存のclaim、明示依頼、または競合の文脈確認が必要な場合だけGit履歴を見る。

対象projectの境界が不明な場合、検索結果が広すぎる場合、必要なsubmoduleや履歴がない場合は、
無制限に探索を続けない。どこまで確認したか、なぜ探索を打ち切ったか、何が未確認かを報告する。

## 出力形式

重要な不一致と根拠不足を先に示す。指摘は次の形式を基本とする。

```text
[DOC↔CONFIG][CONTRADICTED][HIGH]
対象claim: READMEには機能が既定で有効と書かれています。
証拠: config/defaults.yaml の enabled は false です。
不一致・不足: 文書と設定の既定値が一致していません。どちらが正しいかは未確定です。
読者への影響: 利用者が有効化状態を誤認する可能性があります。
修正案・追加確認: source of truthを確認し、READMEまたは設定を更新してください。
```

`HIGH / MEDIUM / LOW` は読者の判断・行動・理解への影響を表す。claimを支持できるかどうかを
示す証拠状態とは分けて扱う。
`VERIFIED` は必要なclaimだけを簡潔に記録し、問題がない文章を改稿する理由にしない。

最後に次を示す。

- 対象文書と確認scope
- claimごとの判定と証拠
- 確認したfile・履歴・citationのledger
- 未実施の検証と理由
- 解消に必要な追加確認

`review` と同様に対象fileを変更しない。改稿も依頼された場合は、校閲結果を確定した後に
明示された改稿モードを適用し、`semantic-preservation.md` の意味保存gateを通す。
