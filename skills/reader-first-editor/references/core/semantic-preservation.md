# 意味保存契約

意味保存は、読みやすさ、自然さ、簡潔さ、JTF表記、Plain Languageの原則より
優先する。書き換えの前後で次の台帳を比較する。

| 項目 | 確認内容 |
|---|---|
| facts | 明示された事実と主張 |
| numbers_and_dates | 数値、単位、日付、時刻、期間 |
| actors | 行為者、判断者、責任主体、受益者 |
| actions / objects | 行為とその対象 |
| conditions / exceptions | 適用条件、前提、例外、但し書き |
| negations | 否定の対象と範囲 |
| causal_relations | 原因、理由、結果、目的、時系列との区別 |
| scope | 対象、期間、環境、数量、修飾の適用範囲 |
| modality | 義務、禁止、許可、推奨、可能性、不確実性 |
| terms / identifiers | 用語、固有名、UIラベル、コード識別子 |
| reader_actions | 読者が行うこと、判断すること |
| required_responses | 返信、承認、提出などの要否と形式 |
| register_and_relationship | 丁寧さ、直接性、距離、謝意、責任の強さ |

## 禁止する意味変化

- 元文にない期限、人物、部署、手順、原因、保証、権利、義務を追加する。
- 条件、例外、否定、但し書き、不確実性を削除する。
- 「必要」を「推奨」に、「可能」を「確実」に変える。
- 「承認」「確認」「共有」「通知」など異なる行為を同一視する。
- 因果関係を相関や時系列に、またはその逆に変える。
- 対象や適用範囲を暗黙に広げる・狭める。
- 技術用語、UIラベル、コマンド、識別子、エラー文字列を無断で変える。
- 敬意、依頼の強さ、責任の所在、対人距離を無断で変える。

## 不足・曖昧さ

不足情報は創作せず、そのまま残すか明示的に指摘する。

```text
原文: 申請書は速やかに提出してください。

不可: 申請書は3月31日までに総務部へ提出してください。

可: 申請書を提出してください。
    期限と提出先は原文から確認できません。[要確認]
```

複数の解釈が成立する場合、`review` では解釈候補と影響を示す。改稿モードでも
勝手に一つを選ばず、原文の曖昧さを保つか確認を求める。

## 比較手順

1. 元文から台帳を作る。暗黙の常識を明示情報として記録しない。
2. 改稿案から独立に同じ台帳を作る。
3. 各項目を `same / explicit-only / changed / missing / added / unclear` で比較する。
4. `changed`、`missing`、根拠のない `added` を修正する。
5. 明確化により暗黙情報を明示した場合は `explicit-only` として、元文から
   一意に導けることを確認する。
6. 解決できない差分は改稿へ混ぜず、提案または質問として分離する。
